# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A terminal/CRT-styled dashboard, deployed to a Raspberry Pi as a dedicated kiosk display. There is no server, no build step, and no bundler — it must keep working exactly as-is: plain `<script src>`/`<link>` tags loaded over `file://`, not ES modules or anything requiring a fetch/import of local files (which `file://` blocks).

**The kiosk starts/restarts solely via reboot — there is no SSH-triggered start/stop.** `setup-kiosk.sh install` enables console autologin + a `.bash_profile` hook that runs `startx` on tty1 boot; after that, a reboot (power loss, `sudo reboot`, etc.) is the only thing that brings the kiosk up. `update` is the one thing still run by hand over SSH (pulls dashboard changes, kills Chromium so `~/.xinitrc`'s loop reopens it fresh) — there's no cron/auto-update. This was a deliberate simplification: an earlier iteration added `xserver-xorg-legacy` + `/etc/X11/Xwrapper.config` (`allowed_users=anybody`) specifically so `start`/`stop` subcommands could work from a plain SSH session too, but that wrapper was explicitly rejected by the user as an unwanted permission-loosening workaround — don't reintroduce `xserver-xorg-legacy`, `Xwrapper.config` edits, or `start`/`stop` subcommands without that being an explicit, deliberate request. An even earlier fully-manual version (no autologin at all) was also tried, after a Wi-Fi-bricking incident on a Pi Zero 2 W, but was reverted too — the cause was never confirmed to be autologin specifically, and going fully manual meant every reboot required a live SSH session just to see the display again.

## Hardware target

- **Raspberry Pi Zero 2 W** — quad-core Cortex-A53 @ 1GHz, 512MB RAM. Modest hardware: keep JS/CSS lightweight (no heavy animations, large images, or expensive per-frame work), and be mindful that this is also driving a full Chromium instance.
- **7" DPI (GPIO parallel) display, IPS panel, no touch, fixed at 1024×600.** This is the one and only viewport — not a responsive range to design for. No touch/pointer interaction handling is needed anywhere in this project (the display is output-only).
- **Design/verify against 1024×600 specifically**, not just "looks fine in a wide browser window" — `html`/`body`/`.grid` all use `overflow:hidden`, so anything that doesn't fit vertically is not scrollable, it's simply invisible on the real device. When checking a layout change, take the verification screenshot at `--window-size=1024,600`, not a larger arbitrary size.

## Commands

There is no build, lint, or test tooling — none is intended. To verify a change actually works, render the page and look at it rather than just reading the code:

```
python -m http.server 8934
```
then open `http://localhost:8934/index.html` (or open `index.html` directly via `file://` — both behave the same way here, since the only network calls are `fetch()`s to external HTTPS APIs, not to local files).

A headless-Chromium screenshot is the fastest way to confirm a UI change rendered correctly end-to-end (all widgets populated, no error/stale states, console clean) without a human in the loop.

## Architecture

**Load order matters.** `index.html` loads scripts in a fixed sequence: `js/config.js` → `js/widget-engine.js` → each `js/widgets/*.js` → `js/bootstrap.js`. Each widget file self-registers by pushing onto a shared global array (`window.KIOSK_WIDGETS`); `bootstrap.js` is the last script and just calls `KioskEngine.mount(window.KIOSK_WIDGETS)` once everything has loaded. New widgets follow this same registration pattern (documented with a template in README.md) and must be added to `index.html`'s script list before `bootstrap.js`. There is no global header — the only on-screen date/time reference is the `calendar` widget itself (`js/widgets/calendar.js`), a normal widget that just happens to "fetch" `new Date()` instead of calling an API, ticking every second via `refreshMs: CONFIG.clockTickMs`. That's the pattern to follow for any other always-fresh, no-network widget.

**The engine owns polling/error state, widgets don't.** `js/widget-engine.js` is the only place that knows about fetch scheduling, retry intervals, stale-data fallback, and the online/offline/stale status dot. A widget definition is just `{ id, title, span, refreshMs?, bare?, showUpdated?, fetch(), render(el, data) }` — `fetch()` returns data or throws, `render()` builds `el.innerHTML` from it. Don't duplicate polling/error-handling logic inside a widget; that all belongs in the engine. Set `bare: true` to render plain content directly on the page background instead of the bordered/titled card (all four current widgets — weather, weather-hourly, calendar, transit-list — use this; there are currently no carded/titled widgets in use, though the engine still supports them and `showUpdated: false` for hiding just the timestamp on one) — the engine skips the title bar entirely for a bare widget, so it also has no status dot/updated stamp; a bare widget builds its own "cardness" via a wrapper div styled in CSS if it wants a background (e.g. `.tl-panel`, `.cal-stampblock`), not the engine's template.

**`js/config.js` is the single source of truth for location/behavior.** Latitude/longitude/timezone drive both weather widgets — `js/widgets/weather.js` (current conditions only) and `js/widgets/weather-hourly.js` (the forecast bar chart), split into two separate widgets/cards specifically so they could be positioned independently in the grid (see below). **There is no air-quality widget** — it existed fused into weather at one point and was removed entirely (dropped as "not necessary"); don't re-add an AQI fetch/render without that being an explicit ask. `CONFIG.transit` is an array of stops, but **not** one-widget-per-stop — `js/widgets/transit.js` registers a single `"transit-list"` widget that `Promise.allSettled`s every configured stop and renders them all as entries in one bare (no card background) departure board: a 2-column CSS grid (`.tl-board`), no divider lines between entries (removed deliberately — a prior version had them, user found them not helpful). Each entry is its own mini-layout: route number beside a block-stacked direction+destination unit (dest lands directly under the direction text because it's a plain block sibling, not a separately-positioned grid cell), with the ETA numbers as the dominant element — see the container-query note below. There's no per-stop service-alert banner currently — dropped when this moved off per-stop cards, would need to be re-added deliberately if wanted. Adding a configured stop is config-only; it just becomes a new board entry.

**The outer `.grid`'s top row is explicitly placed per-widget, not auto-flowed.** `css/style.css` has `.card[data-widget="weather"]`, `="calendar"`, `="weather-hourly"`, `="transit-list"` rules with their own `grid-column`/`grid-row` — weather stacks over calendar in column 1 (rows 1–2), `weather-hourly` fills the remaining 2×1 area beside them (spanning both rows), and `transit-list` takes the full-width row below (row 3, `1fr`, matching `grid-template-rows: auto auto 1fr`). None of these four widgets set `span` in their JS definition anymore — the old `[data-span="2"/"3"]` generic-span CSS was removed since nothing uses it now (everything with a non-default position gets its own explicit `[data-widget=...]` rule). If a widget's grid position needs to change, edit its selector here, not a `span` field in the widget file.

**The ETA numbers use CSS container queries (`container-type: size` + `cqh` units) to scale with row height, not a fixed font-size.** `.tl-eta-row` is the query container; `.tl-eta-num`'s `font-size: 72cqh` means "72% of that container's height," so the number grows/shrinks automatically as `.tl-board`'s rows resize (e.g. when the stop count changes and `grid-auto-rows: 1fr` redistributes height). This requires `.tl-entry`'s `align-items: stretch` (not `center`/`end`) so `.tl-eta-row` actually receives the entry's full height to size against — an item that isn't stretched has only its intrinsic content height, and `cqh` against that is a no-op. If the ETA numbers ever look wrong after a layout change, check that stretch chain first before touching the `cqh` percentage. The percentage itself was tuned empirically (90cqh overflowed horizontally on narrower entries — cqh scales off height but the glyph is wide too — 72cqh was the largest that didn't clip); re-tune by screenshot if the entry width/column count changes.

**External APIs are free/keyless by design** — Open-Meteo (weather) and TTC's public NextBus/Umo IQ feed (`retro.umoiq.com`) at transit. Keep it that way; a widget requiring a paid API or an account/API key is a bigger ask than it looks and should be flagged rather than assumed. Two quirks specific to the TTC feed worth knowing before touching `transit.js`: the `direction` field in a predictions response is a bare object for a single-direction stop, an array for a multi-direction stop, and absent entirely when nothing is due — always normalize before iterating (see `asArray()`). And the `messages` (service alert) endpoint's own `r=` route filter is unreliable (it errors on some valid route tags), so the widget fetches the agency-wide message list and filters client-side by route tag instead of trusting the API's filter.

**Visual theme is closed over CSS custom properties.** `css/style.css` defines the entire amber palette as `:root` variables (`--amber`, `--amber-bright`, `--amber-dim`, `--red`, `--text`, `--text-dim`, `--bg`/`--bg-panel`, etc.). New widget UI should compose from the existing `.card`/`.card-titlebar`/`.card-body` shell and reuse these tokens rather than introducing new colors or one-off styling. Current direction — "premium transit display," explicitly *not* a literal DOS/CLI terminal — landed after two rounds of live iteration: dark charcoal (`--bg:#12110f`) with cards only subtly lighter (`--bg-panel:#171611`), **no card border at all** (the two background tones plus rounded corners plus generous padding are what read as a "card," not a stroke), no scanline/CRT overlay, no decorative glow — except one deliberate exception: `.tr-urgent` (an arriving-≤5-min bus) gets a soft `text-shadow` glow on its big number, the one accent allowed to break the flat/glow-free rule because it's meaningful (data-driven), not decorative. Titles dropped the `>` CLI prompt character entirely. Don't reintroduce a card border, scanlines, or ambient glow without that being an explicit, deliberate request — but do follow the "one deliberate accent for meaningful state" pattern if a similar signal (e.g. an alert, a threshold) comes up elsewhere.

**A flex child can safely use `flex:1`/`justify-content:space-between` to fill dead space inside an already-sized card** — this does **not** reintroduce the grid-shrink bug below: that bug is about `.grid`'s own sizing as a flex item, not about a flex child distributing space inside a `.card` whose height the grid has already settled on. A card's *natural* (ungrown) content size is what the grid row's `auto` height is computed from; `flex:1` + `justify-content:space-between` on a child only distributes space *after* that row height is established. Useful if dead space becomes a complaint again on some future widget.

**Grid rows and `overflow:hidden` interact badly when content overflows — don't debug this from first principles again.** `.grid` is a flex item (`flex:1`) inside a fixed-height `body`, and it also has `overflow:hidden` (required — no scrolling is possible on this display). That combination makes `.grid` a flexbox "scroll container," which per spec zeroes out its automatic minimum size instead of basing it on content; the practical effect is that if the widgets' total natural height exceeds the available ~546px, CSS Grid's `auto`-sized rows shrink **proportionally across every row**, not just the last one — so a too-tall layout doesn't overflow visibly at the bottom, it clips a little off of every single card uniformly, which looks like a mystifying per-card bug rather than what it actually is (not enough room). If a widget change makes things not fit again, the fix is reducing content height (tighter markup, fewer list items, more compact formatting), not chasing it as a CSS clipping bug.
